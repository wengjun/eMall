# 101 什么是舱壁隔离？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

舱壁隔离来自船舱设计：一个舱进水不能让整艘船沉没。软件系统中，它指把资源按业务、下游或优先级隔离，
让一个局部故障不会耗尽全部资源。常见实现包括线程池隔离、连接池隔离、信号量隔离、实例隔离和队列隔离。

它的目标是限制故障半径，保住核心能力。

## 为什么需要舱壁隔离？

大型电商系统依赖很多下游。

如果所有请求共享同一批资源：

- 库存慢会拖垮订单。
- 推荐慢会影响商品详情。
- 报表任务会挤占交易资源。
- 非核心任务会影响核心支付。

舱壁隔离就是防止这些问题互相传染。

## 常见隔离方式

常见方式：

- 线程池隔离。
- 信号量隔离。
- 数据库连接池隔离。
- HTTP 连接池隔离。
- MQ topic 或 consumer group 隔离。
- Kubernetes 资源隔离。
- 服务实例隔离。
- 队列隔离。

隔离可以发生在代码层、资源层和部署层。

## 线程池隔离

不同下游使用不同线程池。

库存线程池打满，不影响支付线程池。

适合阻塞调用和慢下游风险较高场景。

代价是线程数和配置复杂度增加。

## 信号量隔离

信号量隔离限制并发数，但不切换线程池。

适合：

- 短耗时任务。
- 非阻塞调用。
- 线程切换成本敏感场景。

它开销低，但隔离强度不如线程池隔离。

## 实例和资源隔离

核心交易服务可以和后台任务分开部署。

例如：

- 订单创建实例。
- 订单查询实例。
- 订单后台补偿实例。

不同实例设置不同 CPU、内存和扩缩容策略。

这比只在进程内隔离更彻底。

## 在 eMall 项目中怎么讲？

eMall 中推荐、广告、营销是非核心能力，订单、库存、支付是核心能力。

推荐服务慢时，商品详情可以降级不展示推荐，但不能影响商品基础信息和下单。

订单服务内部也要把库存、支付、风控调用隔离，防止一个下游拖垮全链路。
