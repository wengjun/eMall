# 112 为什么数据库唯一键通常比分布式锁更可靠？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

数据库唯一键把并发约束放在最终写入资源的地方，由数据库原子保证，不依赖客户端是否正确加锁、锁是否过期或网络是否正常。
分布式锁只能降低并发冲突，不能替代最终一致性约束。

对防重复下单、优惠券领取、支付回调幂等这类场景，唯一键和幂等表通常比锁更可靠。

## 锁是外部协调

分布式锁在资源外部做协调。

风险包括：

- 锁过期。
- 误删锁。
- 续约失败。
- 网络分区。
- 客户端暂停。
- 代码忘记释放。

锁成功不代表后续写入一定正确。

## 唯一键是资源端约束

数据库唯一键直接作用在最终数据上。

例如：

```sql
unique(user_id, coupon_id)
```

无论多少实例同时插入，数据库只允许成功一条。

这是资源端原子约束。

## 幂等场景

支付回调可能重复到达。

可以设计：

```sql
unique(payment_no)
```

第一次处理成功，后续重复请求插入失败或查到已处理结果，直接返回成功。

这比先抢分布式锁再写库更可靠。

## 唯一键不是万能

唯一键适合防重复。

它不能解决所有问题，例如：

- 复杂跨表事务。
- 长流程互斥。
- 外部资源调用。
- 高并发热点更新性能。

但对于“最多只能有一条记录”的场景，它是最直接的正确性保障。

## 在 eMall 项目中怎么讲？

优惠券领取应使用唯一键防重复：

```text
user_id + coupon_id
```

订单创建可使用业务幂等号：

```text
client_request_id unique
```

分布式锁最多用于减少冲突，不作为唯一正确性保障。
