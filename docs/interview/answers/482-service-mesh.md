# 482 Service Mesh 解决什么问题？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

Service Mesh 解决服务间通信治理问题，把流量控制、安全、可观测性和可靠性从业务代码中下沉到基础设施层。
典型能力包括服务发现、负载均衡、重试、超时、熔断、限流、灰度路由、mTLS、访问策略和调用指标采集。

## 为什么需要 Service Mesh

微服务系统里，每个服务都需要处理调用超时、重试、熔断、trace、指标、安全和灰度。如果这些能力都由业务 SDK 实现，
不同语言、不同团队、不同版本会产生治理不一致。Service Mesh 通过 sidecar 或节点代理统一承载这些横切能力。

它的价值不是替代业务逻辑，而是让服务间通信规则可声明、可审计、可统一演进。

## 核心组成

Service Mesh 通常分为数据平面和控制平面：

- 数据平面负责真实流量转发，例如 Envoy sidecar。
- 控制平面负责下发路由、安全、策略和证书配置。

业务服务只调用本地代理，代理再根据控制面策略访问目标服务。

## 能解决的问题

Service Mesh 常见场景包括：

- 统一 mTLS，实现服务间身份认证和加密传输。
- 统一超时、重试、熔断和故障注入。
- 按版本、用户、header、权重做灰度路由。
- 自动采集请求量、错误率、延迟和 trace。
- 通过访问策略限制服务间调用关系。

## 代价和边界

Service Mesh 会增加系统复杂度、运维成本、资源消耗和排障难度。代理本身也可能引入延迟和新的故障面。
因此不是所有团队都应该一开始上 Mesh。只有当微服务数量、语言多样性和治理复杂度达到一定规模时，收益才明显。

## 电商系统实践

大型电商系统如果进入多团队、多语言、多集群阶段，可以用 Service Mesh 统一治理订单、支付、库存、风控之间的调用。
但在当前 Java17 微服务项目中，也可以先通过网关、Resilience4j、Micrometer 和 Kubernetes 完成核心治理，
等规模扩大后再引入 Mesh。
