# 227 如何处理跨 partition 乱序？

[返回按分类学习面试题](../README.md)

## 题目

如何处理跨 partition 乱序？

## 先给面试官的短答案

跨 partition 通常无法保证全局顺序，因此业务设计要避免依赖全局有序。
如果需要同一业务对象有序，应使用同一个 key 路由到同一 partition；如果必须处理跨对象顺序，要用版本、时间水位、状态机或聚合读模型解决。

分布式消息系统里，全局顺序通常代价很高，不应轻易要求。

## 为什么会乱序？

原因包括：

- 不同 partition 并行处理。
- 不同消费者速度不同。
- 重试和死信重放。
- 网络延迟不同。
- 生产者并发发送。

MQ 通常只承诺单 partition 内顺序。

## 处理思路

处理方式：

- 避免全局顺序需求。
- 以业务 key 保证单对象顺序。
- 使用事件版本。
- 使用状态机拒绝非法回退。
- 对聚合场景使用最终一致读模型。
- 对乱序事件做短暂缓冲。

不要为所有消息强行单 partition，这会牺牲吞吐。

## 什么时候需要全局顺序？

全局顺序很少真正需要。

如果是资金流水、审计日志等强顺序场景，可以按账户或业务主体分区，而不是全系统单一顺序。

全局单队列会成为性能瓶颈。

## 在 eMall 项目中怎么讲？

不同订单之间不需要全局顺序。

同一订单用 `orderId` 分区即可。数据仓库做全局报表时，可以按事件时间和水位线处理迟到事件，而不是要求 MQ 全局有序。

## 共性一致性模型

状态机、Outbox、幂等、重试、对账和补偿的统一闭环及 Java 17 示例见
[共享模型：最终一致、状态机和补偿](../shared-answer-models.md#最终一致状态机和补偿)。

## 专家级完整回答

```text
跨 partition 不能依赖全局顺序。正确做法是把有顺序要求的业务对象用同一个 key 路由到同一 partition，
并在消费者侧使用版本和状态机处理重复、乱序和旧事件。

对跨对象聚合查询，应通过最终一致读模型、事件时间和水位线处理，而不是牺牲吞吐追求全局有序。
```

## 回答评分点

高分答案应该覆盖：

- MQ 通常只保证单 partition 顺序。
- 避免不必要的全局顺序需求。
- 同一业务对象用同一 key。
- 版本和状态机处理乱序。
- 全局顺序会牺牲吞吐。
