# 679 为什么不能依赖本地时钟判断分布式事件顺序？

[返回按分类学习面试题](../README.md)

## 根本原因

不同机器的物理时钟无法保持完全同步。晶振会漂移，NTP/PTP 校时有误差，系统时间还可能向前跳或向后拨；虚拟机暂停和进程调度只会让观测更复杂。因此“时间戳更大”不等于事件在因果上更晚。

```text
节点 A 实际先写，时钟显示 10:00:00.500
节点 B 实际后写，时钟显示 10:00:00.200
```

若用 last-write-wins 比较这两个时间戳，先发生的 A 反而覆盖后发生的 B。

## 四类时钟分别能做什么

- **墙上时钟**：对应日期时间，适合展示、审计和业务日切，不适合测量本地耗时或生成全局顺序。
- **单调时钟**：只保证单机内递增，Java 中用 `System.nanoTime()` 计算耗时，不能跨进程比较或持久化为业务时间。
- **Lamport Clock**：若 A 因果先于 B，则 `L(A) < L(B)`；反过来不成立，无法判断并发。
- **Vector Clock**：可判断先后与并发，但元数据随参与者增长，动态大集群成本高。

Hybrid Logical Clock 把近似物理时间和逻辑计数结合，既保留接近现实时间的可读性，又能维持因果单调，但仍要把时钟不确定区间纳入协议。

## Java 中最容易犯的错误

```java
long started = System.nanoTime();
try {
    callDownstream();
} finally {
    Duration elapsed = Duration.ofNanos(System.nanoTime() - started);
    latencyRecorder.record(elapsed);
}
```

测耗时应使用单调时钟，而不是两次 `Instant.now()` 相减。业务过期时间仍应保存为 `Instant`，但安全协议不能仅凭应用节点认为“已过期”；数据库条件、租约服务或资源端版本才是裁决者。

## 事件排序的正确方式

- 同一订单内使用数据库版本号、事件序号或 Kafka 单分区偏移量建立顺序。
- Leader 变更使用 term/epoch，先比较任期，再比较日志索引。
- 并发可合并数据使用向量版本、CRDT 或显式冲突解决。
- 审计同时记录业务时间、服务接收时间、持久化时间、事件序号和 trace ID，不能只留一个 `created_at`。

## eMall 场景

订单超时关闭与支付成功可能并发。不能通过比较两个服务的 `createdAt` 决定胜负，而应在订单聚合上执行带预期版本的状态转换：
支付命令只有在允许状态和版本匹配时提交，否则进入人工或补偿流程。这样正确性来自状态机和原子条件，
而不是假设所有机器时间一致。
