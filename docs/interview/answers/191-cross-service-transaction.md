# 191 跨服务事务怎么处理？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

大型微服务系统通常避免全局大事务，优先使用本地事务、状态机、可靠消息、幂等、补偿和对账来实现最终一致。
只有在强一致收益明显且规模可控的场景，才考虑 TCC 或 2PC。

跨服务事务的核心不是“让所有服务同时提交”，而是让业务状态可恢复、可补偿、可验证。

## 为什么不用全局事务？

全局事务问题包括：

- 锁持有时间长。
- 参与者故障会阻塞。
- 网络抖动影响提交结果。
- 吞吐量低。
- 跨团队服务耦合严重。

电商下单、支付、库存这些链路流量大，不能把所有服务绑在一个长事务里。

## 常见方案

常见方案：

- 本地事务加 Outbox。
- Saga 编排或协同。
- TCC 预留、确认、取消。
- 状态机驱动补偿。
- 定时对账和修复。

选择取决于业务是否可补偿、是否需要资源预留、延迟是否可接受。

## 关键保障

必须具备：

- 幂等。
- 去重。
- 状态机。
- 可靠消息。
- 失败重试。
- 死信恢复。
- 对账任务。
- 操作审计。

没有这些保障，最终一致只是口号。

## 电商系统实践

下单时订单服务先创建待支付订单，库存服务做库存预占，支付成功后订单状态变为已支付。

如果库存预占失败，订单进入失败或取消状态；如果支付成功但订单更新失败，通过支付事件重试和对账任务修复。
