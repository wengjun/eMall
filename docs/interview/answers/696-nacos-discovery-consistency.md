# 696 Nacos 服务发现的一致性、订阅和本地缓存如何工作？

[返回按分类学习面试题](../README.md)

## 先明确资源层次

已有服务注册中心开发经验时，心跳、订阅和本地缓存的通用原理可以跳过；这里重点记 Nacos 的资源模型、
实例类型和客户端容灾行为。

Nacos 实例归属于 namespace、group、service 和 cluster。namespace 常做环境或租户隔离，group 区分业务分组，
cluster 表示机房/地域等就近路由单元。调用方的服务键必须包含这些维度，不能只用 service name 猜测唯一性。

## 临时实例与持久实例

临时实例更偏向 AP/Distro 风格，客户端断连或健康租约失效后可被自动摘除，适合可随时重建的应用实例。持久实例的元数据管理偏向 CP，一般需要显式注销，适合不能因一次心跳中断就消失的固定端点。

选择依据是实例生命周期和故障语义，不是“CP 一定更高级”。应用 Pod 若注册成持久实例，异常销毁后可能长期留下脏地址。

## 订阅不是把完整状态永远推到客户端

Nacos 3.x SDK 通过长连接接收服务变化通知，客户端随后维护最新实例视图。推送是尽力而为，客户端还要具备重新查询、重连 redo、内存缓存和本地磁盘快照能力。

```text
Provider 注册/续约 -> Nacos 服务状态
                         -> 变更通知 -> Consumer 本地实例表
Consumer 调用 -> 本地路由/负载均衡 -> Provider
```

注册中心短暂不可用时，Consumer 可用本地快照继续调用已知实例；代价是地址可能陈旧，所以连接失败要触发被动淘汰和重查，不能无限相信磁盘缓存。

## 健康、注册和可调用不是同一件事

实例出现在 Nacos 中不代表已经完成 JVM 预热、数据库连接建立和缓存加载。正确启动顺序是先通过本地 readiness，再注册或把权重逐步提升；下线时先降低权重/摘流量、等待在途请求，再注销和停进程。

Consumer 还应按 cluster 优先就近路由，并在本地无可用实例时明确跨机房回退策略。保护阈值可避免大面积误摘除导致剩余实例雪崩，但可能把部分请求送到不健康实例，因此只能作为故障权衡。

## 生产观测和测试

监控服务端成员状态、订阅延迟、客户端视图版本、空地址次数、缓存地址调用失败率、注册续约失败和跨 cluster 回退量。故障测试要覆盖 Nacos 全部不可达、推送丢失、客户端重启读取快照、Provider 无优雅下线和机房分区。

在 eMall 中，Dubbo Consumer 不会把 Nacos 可用性放到每次请求同步路径；本地视图承接短故障，同时用有限超时、熔断和 stale-address 指标控制陈旧风险。
