# 598 你为什么要拆 common？

[返回按分类学习面试题](../README.md)

## 核心判断

common 只承载跨模块稳定且与具体业务域无关的契约与基础能力，例如错误模型、事件信封和可复用治理组件。目的是消除高风险重复实现，不是把所有“暂时不知道放哪”的代码集中起来。

## 取舍依据

- 只有至少两个模块确实需要、语义一致且变化频率低的能力才考虑抽取。
- 业务实体、Mapper、领域 Service 和某个服务的配置不能进入 common。
- API、实现和自动配置应拆开，调用方只依赖最小契约。
- 公共依赖要版本化、兼容测试并有 owner，否则一次修改会扩大爆炸半径。

## 项目证据与边界

eMall 的公共模块聚焦 API、事件、幂等和治理原语，各领域仍拥有自己的模型与数据访问。少量重复通常比错误抽象便宜，应在重复模式稳定后再提取。
