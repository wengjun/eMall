# 681 如何设计不会产生双主写入的领导者选举？

[返回按分类学习面试题](../README.md)

## 先说严格结论

不能承诺物理世界中任意时刻只有一个进程“自认为是 Leader”；旧进程可能暂停后恢复。能够承诺的是：任意时刻只有持有当前多数派授权和最新 fencing term 的节点，其写入会被权威资源接受。

## 一个可落地的协议

1. 在强一致协调存储中维护 `leaderId`、单调 `term`、租约到期信息和配置版本。
2. 候选者通过比较并交换操作获取领导权；获取成功时原子增加 term。
3. 候选者必须获得当前成员多数派确认，成员变更采用联合多数派，不能直接替换名单。
4. Leader 的每次写都携带 term；数据库或下游只接受 `term >= accepted_term` 的原子更新。
5. Leader 失去续租、失去多数派或看到更高 term 后立即停止接收新命令，但安全性不依赖它是否及时停止。

资源端示意：

```sql
UPDATE shard_owner
SET payload = ?, accepted_term = ?
WHERE shard_id = ? AND accepted_term <= ?;
```

真实实现通常还会校验业务版本，防止同一 term 内并发覆盖。

## 切换期间如何处理客户端

- 对外先停止旧路由，再等待在途请求排空，但不能把排空当作唯一安全措施。
- 新 Leader 在服务前恢复已提交日志或确认数据库复制位点，不能只因注册中心显示健康就接流量。
- 写超时返回“结果未知”，客户端携带原幂等键查询或重试。
- 客户端缓存的旧 Leader 地址必须受版本约束；收到 `NOT_LEADER` 后刷新路由。

## 容易失败的方案

- Redis `SET NX EX` 后直接写不支持 token 的下游。
- 两节点互相心跳，谁看不到对方谁当主。
- 用机器时间或 UUID 判断新旧 Leader。
- 先更新注册中心、后恢复数据，导致新主接受建立在旧快照上的写。
- 运维同时在两个机房执行“强制提升”。

## 如何证明和测试

安全不变量是“对每个资源，成功写入的 term 单调不降，且同一业务版本至多提交一次”。测试应随机暂停 Leader 超过 TTL、切断不同方向网络、延迟复制、并发强制切换，再审计所有成功写入的 term 和业务版本。

在大型电商系统的分片任务调度中，Nacos/数据库可提供候选协调，但任务表必须保存 `owner_term` 并条件更新。
这样即使旧 JVM 因 Stop-The-World 恢复，仍只能收到 stale-term 拒绝，不能执行第二次结算。
