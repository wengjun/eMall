# 675 CAP 和 PACELC 应该如何正确理解？

[返回按分类学习面试题](../README.md)

## 面试时先纠正两个误区

CAP 不是让系统平时从 C、A、P 中任选两个。网络分区发生时 P 已经是客观条件，系统只能针对某个操作选择：继续接受可能冲突的请求，或者拒绝一部分请求以维持一致性。

PACELC 补上了正常时期的取舍：**如果发生分区（P），在可用性（A）和一致性（C）之间选择；否则（E），在延迟（L）和一致性（C）之间选择。**

## CAP 中三个词的精确定义

- C 通常指线性一致性，而不是数据库 ACID 中的约束一致性。
- A 指每个发给未故障节点的请求最终都收到非错误响应，不等同于“四个九”的业务 SLA。
- P 指系统必须在节点间消息任意丢失或延迟时仍有明确行为，不是一个可以关闭的产品选项。

假设主库与从库失联：

```text
客户端 A -> 主库：库存 1 -> 0
                 X 网络分区 X
客户端 B -> 从库：是否也允许库存 1 -> 0？
```

从库拒绝写，牺牲分区侧可用性但保护库存不超卖；从库接受写，两个分区都可服务，但必须面对冲突和双重承诺。对于库存，这种冲突通常无法靠事后合并挽回。

## PACELC 为什么更贴近架构决策

没有分区时，跨地域强一致写仍要等待远端多数派，延迟至少受网络往返时间约束。异步复制读得快，却可能读到旧数据。因此架构评审不能只问“系统是 CP 还是 AP”，还要问：

- 正常情况下读是否必须经过 Leader 或 Quorum？
- 写成功需要本机落盘、同机房副本，还是跨地域多数派？
- 允许多长陈旧窗口，能否提供读己之写？
- 分区时哪些命令必须失败，哪些可以降级为排队或只读？

## 按业务命令选择，不给整个系统贴标签

同一个大型电商系统内，不同服务可以采用不同策略：

- `reserveInventory` 在无法确认权威库存时失败或排队，偏向 PC。
- 商品详情读取在副本落后数秒时仍返回，偏向 PA/EL。
- 优惠券核销必须保护“一券一次”，但营销素材读取可以陈旧。
- 订单查询可回退到旧快照，订单状态变更不能在失去主权时继续写。

## 高质量回答应落到失败契约

必须明确超时之后客户端能知道什么。超时只代表“结果未知”，不代表操作失败；客户端应使用同一个幂等键查询或重试，而不是生成新请求。系统还要暴露复制位点、Quorum 可达性、拒绝写次数和收敛延迟。

因此，CAP/PACELC 的价值不是给技术选型贴标签，而是迫使设计者写清每条命令在网络不可靠和跨地域延迟下的业务语义。
