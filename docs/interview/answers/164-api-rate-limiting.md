# 164 如何做接口限流？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

接口限流要把系统容量转换成客户端可理解的配额契约。需要明确身份维度、持续速率、突发额度、
统计周期、优先级以及超限后的 HTTP 响应，不能只在服务内部配置一个 QPS 数字。

本题重点是 API 契约；通用限流架构和算法选择见[如何设计限流](250-rate-limiting-design.md)。

## 身份与配额维度

常见维度：

- IP。
- userId。
- appId。
- merchantId。
- API path。
- tenant。
- region。
- API 套餐和全局容量。

应先使用已认证的 appId、userId 或 merchantId，再把 IP 和设备作为风控辅助维度。只按 IP 限流会误伤
共享出口用户，也容易被代理池绕过。

## 配额模型

API 配额通常同时包含：

- 持续速率，例如每秒 100 次。
- 突发额度，例如短时间允许 200 次。
- 日或月累计额度。
- 单个高成本接口的独立权重。
- 支付回调、内部补偿等高优先级保留额度。

配额来自容量测试、下游预算和商业套餐，并通过灰度变更，不能拍脑袋配置。

## 执行位置与一致性

入口网关负责身份和套餐配额，业务服务负责 SKU、商家或下游等资源级保护。单机计数成本低但只能约束
单实例；严格的全局额度需要 Redis Lua 或集中式配额服务，并明确计数系统故障时开放还是关闭。

## 客户端响应契约

被限流应返回：

- HTTP 429。
- 稳定的业务错误码。
- `Retry-After` 或明确的下一次可尝试时间。
- `traceId` 和可选的剩余额度信息。

客户端必须指数退避并增加 jitter。服务端不能让超额请求进入内部长队列，否则限流会退化成高延迟和超时。

## 在 eMall 项目中怎么讲？

开放 API 按 appId、商家、接口权重和套餐限流，返回 429 与 `Retry-After`。秒杀接口额外按活动、SKU
和用户限流；支付回调使用独立高优先级额度，不能与普通查询共享预算。
