## 页内怎样定位记录

InnoDB 默认以固定大小的页作为缓存和 IO 基本单位。索引页包含文件头、页头、`infimum`/`supremum` 伪记录、
用户记录、空闲空间、page directory 和校验尾部等区域。

页内用户记录按键形成链，page directory 保存分组槽位。查找先对槽位做二分，再在小范围记录链上比较，
不是从页首线性扫描所有行。删除通常先留下可复用空间和删除标记，后台 purge 与后续页整理决定何时真正回收。

## 页分裂如何发生

当目标叶子页没有足够连续空间容纳新记录时，InnoDB 分配新页、移动部分记录、调整父节点指针并产生更多 redo。随机分布主键会把写入散布到大量中间页，增加缺页、分裂和缓存工作集。

```text
插入前: [10 20 30 40 | 满]
插入 25
分裂后: [10 20] -> [25 30 40]
```

递增主键主要写 B+Tree 右侧，局部性好，但极高并发下也可能形成最右页 latch 热点。选型是随机写放大与单点热点之间的权衡，不是“UUID 永远错”或“自增永远快”。

## 行过宽会带来什么

变长大字段可能把部分内容存到溢出页，聚簇记录保留指针和必要前缀。读取大字段需要额外页访问；即使接口不用该字段，`SELECT *` 也会增加网络、反序列化和 Buffer Pool 压力。

合理做法包括冷热字段拆表、只选择所需列、限制无界文本、把大对象放对象存储并在数据库保存元数据。拆表必须基于访问模式，不应为“范式漂亮”增加每次核心查询的 join。

## 二级索引写放大

每次订单行更新可能同时维护多个二级 B+Tree。非唯一二级索引页不在 Buffer Pool 时，部分变更可进入 change buffer 后再合并；唯一索引必须先确认唯一性，不能按同样方式延迟检查。

索引越多，提交生成的 redo、页脏化和复制流量越大。要用实际查询收益证明每个索引存在的价值。

## 电商系统设计示例

- 压测内部订单 ID 的随机写分布和右侧热点，按真实并发选择，而不是只比较 ID 生成速度。
- 查询“用户最近订单”建立 `(user_id, created_at, id)` 复合索引，并使用 seek pagination。
- 商品详情大文本和媒体 URL 与高频库存行分离，避免一次详情更新污染库存热点页。

诊断时联看页分裂、索引大小、Buffer Pool 缺页、redo 速率和 SQL 实际扫描行数。只调整页参数而不修正主键、行宽和索引数量，通常治标不治本。
