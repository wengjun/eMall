# 687 MySQL 主库切换如何控制数据丢失和脑裂？

[返回按分类学习面试题](../README.md)

## 切换不是“把只读改成可写”

一次安全切换至少要完成旧主隔离、候选数据比较、提升、路由变更、拓扑重建和旧主处置。任何自动化系统如果只做健康检查和修改 VIP，都可能把暂时卡顿放大成双主或数据丢失。

## 推荐顺序

1. 判定故障并冻结自动化，防止多个控制器同时操作。
2. 对旧主执行网络、存储或云 API 级 fencing；仅调用 MySQL `read_only` 不足以证明隔离。
3. 收集各候选的 GTID executed set、relay/applier 状态和持久化健康度。
4. 选择包含最完整已确认事务且没有分叉历史的候选者，必要时先应用 relay log。
5. 以新的拓扑 epoch 提升，验证可写、数据约束和关键查询。
6. 更新代理/服务发现并让旧连接排空；客户端重连后校验新 epoch。
7. 其余 Replica 从新主补齐，旧主不能未经重建直接回归。

## RPO 如何计算

异步复制的潜在丢失量是故障时尚未到达候选者的已提交事务。半同步把成功返回事务至少复制到一个确认节点，但如果提升的不是该节点，或者系统在超时后退化为异步，仍会丢失。

因此候选选择必须基于实际 GTID 集合，不是固定优先级。RPO 报告要区分“客户端收到成功”和“客户端超时但可能提交”的事务。

## 防止旧主重新写入

- 数据库访问代理为拓扑携带 epoch，拒绝旧 epoch 后端。
- 旧主使用独立凭据撤销、网络隔离或云实例 fencing。
- 外部任务和 CDC 也必须切换，避免仍从旧主产生副作用。
- 恢复网络后将旧主作为全新 Replica 重建，不能直接双向合并交易数据。

## 应用必须配合

切换期间连接会断开，事务结果可能未知。Java 服务应使用有限连接超时、连接池失效检测和同一幂等键重试；不能无界重试非幂等写。订单创建返回前写入的业务请求号，是切换后确认结果的依据。

## 演练验收

演练同时注入 Source 进程崩溃、整机隔离、单向网络分区和半同步退化。验收包括：无双主成功写、成功响应数据不超出声明 RPO、路由收敛时间满足 RTO、CDC 无重复副作用、旧主不能自行回归。

高质量回答应给出安全优先级：如果无法 fencing 旧主，就宁可延长不可写时间，也不冒险提升新主承接库存和支付写入。
