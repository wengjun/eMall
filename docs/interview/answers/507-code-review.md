# 507 如何做代码评审？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

代码评审要优先看正确性、边界、并发、安全、可维护性、测试和可观测性，而不是只看格式。好的评审要理解需求、
检查设计假设、关注失败路径，并给出具体、可执行的建议。

## 评审顺序

先看需求和范围：这个变更解决什么问题，是否有不必要的扩大范围。

再看设计和接口：模块边界是否清晰，接口是否稳定，是否破坏兼容。

然后看核心逻辑：状态机、金额、幂等、事务、并发、异常处理和数据一致性是否正确。

继续看测试：是否覆盖正常、边界、异常、并发和回归场景。

最后看运维：日志、指标、告警、配置、灰度和回滚是否具备。

## 评审方式

评审意见要具体。例如不要只说“这里不好”，而要说明风险、影响和建议改法。

要区分阻塞问题和建议问题。会导致 bug、安全风险、数据损坏的问题必须阻塞；命名和微小风格问题可以建议。

评审不应变成个人偏好争论，团队规范能自动化的尽量交给工具。

## 电商系统实践

大型电商系统的订单、支付、库存相关 PR 要重点评审事务边界、状态流转、幂等、补偿、Outbox 和测试。
商品展示或推荐类 PR 可以更关注性能、缓存、降级和用户体验。
