# 509 如何设计公共模块，避免 common 变成垃圾桶？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

公共模块应只放稳定、通用、无业务归属或跨模块明确复用的能力，并按职责拆分边界。不能把临时工具类、
业务 DTO、特殊规则和某个服务私有逻辑随便放进 common。公共模块要有 API 设计、版本管理、依赖控制和评审门槛。

## 什么适合放公共模块

适合放公共模块的内容包括统一异常模型、错误码基础类型、时间工具、金额值对象、签名工具、脱敏工具、
分页模型、trace 上下文、幂等基础组件和可观测性封装。

这些能力应该稳定、通用、依赖少，并且不反向依赖具体业务服务。

## 什么不应该放

不应该把订单私有 DTO、某个促销规则、某个支付通道适配器、临时转换工具、复杂业务判断放进 common。
否则 common 会逐渐变成所有模块都依赖、没人敢改、发布困难的垃圾桶。

公共模块越大，模块耦合越强，变更影响面越不可控。

## 设计原则

公共模块要按能力分层，例如 `common-core`、`common-web`、`common-security`、`common-observability`。
如果项目保持单个 common，也要在包结构上清晰分域。

公共 API 要稳定，避免暴露内部实现。依赖要向内收敛，不能让 common 依赖业务模块或重型基础设施。

## 在 eMall 项目中怎么讲？

eMall 的 `common` 可以承载错误模型、Money、签名、脱敏、幂等基础和 HTTP 客户端封装。
但订单状态、支付通道规则、促销计算和库存策略应留在各自模块，最多抽象成明确接口。
