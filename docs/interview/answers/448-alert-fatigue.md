# 448 告警为什么不能太多？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

告警太多会造成告警疲劳，值班人员无法分辨真正重要的问题，最终导致关键告警被忽略。好的告警应该
是可行动、低噪声、能反映用户或业务影响。

告警系统的目标不是把所有异常都叫醒人，而是让人处理真正需要人工介入的问题。

## 告警过多的问题

问题：

- 值班人员疲劳。
- 关键告警被淹没。
- 大量误报降低信任。
- 处理优先级混乱。
- 团队开始忽略告警。

告警失去可信度后非常危险。

## 好告警标准

标准：

- 有明确影响。
- 有明确负责人。
- 有处理动作。
- 有 Runbook。
- 低误报。
- 能自动恢复则不叫醒人。

不可行动的告警应降级为记录或工单。

## 降噪方式

方式：

- 按服务和依赖聚合。
- 抑制级联告警。
- 使用 SLO burn rate。
- 区分通知和报警。
- 设置维护窗口。
- 定期清理无用告警。

告警也需要持续治理。

## 治理闭环

每条告警都应记录触发次数、确认率、真实事故率、响应时间、负责人和 Runbook。需要立即人工处理且影响用户的
信号才进入页面告警；容量趋势和低风险异常进入工单或日报。

团队应定期复盘误报、漏报和重复页面，删除没有处置动作的规则，并用历史事故回放验证新阈值。

## 在 eMall 项目中怎么讲？

eMall Redis 故障时，可能同时触发缓存命中率下降、数据库 QPS 升高、接口 P99 升高和错误率升高。

告警系统应聚合为一条核心事故告警，并保留相关信号，而不是给值班人员推送几十条重复通知。
