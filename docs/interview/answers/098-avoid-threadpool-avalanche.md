# 098 如何避免线程池雪崩？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

线程池雪崩通常来自下游慢、任务堆积、线程占满、队列上涨、超时重试和资源耗尽。避免方式是有界队列、
隔离线程池、合理超时、限流、熔断、降级、拒绝策略、取消机制和监控告警。

核心原则是让慢依赖局部失败，不要拖垮整个服务。

## 雪崩链路

典型链路：

```text
下游变慢 -> 工作线程被占住 -> 队列堆积 -> 内存上涨 -> GC 抖动 -> 请求超时 -> 重试放大 -> 服务崩溃
```

线程池雪崩不是单点问题，而是一串连锁反应。

## 有界队列

无界队列会让任务无限堆积。

有界队列能在容量耗尽时及时触发拒绝、限流或降级。

这是防止内存被拖垮的基础。

## 超时控制

下游调用必须有超时。

包括：

- 连接超时。
- 读取超时。
- 整体调用超时。
- 异步任务超时。

没有超时，线程可能长时间被占住。

## 线程池隔离

不同下游或业务不应该无脑共享线程池。

库存慢不应该占满支付查询线程。

搜索慢不应该影响订单创建。

隔离能限制故障影响范围。

## 熔断和降级

当下游持续慢或错误率高，要熔断。

熔断后：

- 不再继续打满下游。
- 快速返回降级。
- 给下游恢复时间。
- 半开探测恢复。

这就是下游自动平滑恢复的重要基础。

## 控制重试

重试必须有边界。

要求：

- 限制重试次数。
- 使用指数退避。
- 加抖动。
- 只重试幂等操作。
- 避免多层同时重试。

盲目重试是雪崩放大器。

## 监控和告警

必须监控：

- active count。
- queue size。
- rejected count。
- task wait time。
- task execution time。
- timeout count。
- 下游错误率。
- 熔断状态。

在线程池打满前就应该告警。

## 在 eMall 项目中怎么讲？

订单服务调用库存服务，如果库存慢，订单服务需要：

- 库存调用独立线程池。
- 超时快速失败。
- 熔断库存下游。
- 队列满时拒绝新请求。
- 返回稍后重试或排队结果。
- 防止前端和服务端重复重试。

这样库存故障不会拖垮订单服务全部能力。
