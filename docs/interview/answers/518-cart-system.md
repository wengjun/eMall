# 518 设计购物车系统

[返回按分类学习面试题](../README.md)

## 题目

设计购物车系统。

## 先给面试官的短答案

购物车系统负责保存用户购买意图，核心能力包括加购、改数量、删除、勾选、合并、跨端同步和结算前校验。
它是高读写、弱交易属性的系统，通常使用 Redis 提供低延迟访问，数据库做持久化和恢复，价格库存在结算时重新校验。

## 核心需求

购物车要支持登录用户和未登录用户。未登录购物车可以存浏览器或设备侧，登录后与服务端购物车合并。

购物车还要支持 SKU 维度数量、勾选状态、加购时间、商家分组、失效商品、价格变更提示和库存不足提示。

## 存储设计

Redis 适合存购物车热数据，例如按 userId 保存 hash 或 sorted set。数据库用于持久化，防止 Redis 数据丢失，
也便于多端同步和历史分析。

购物车不是订单，不能长期相信加购时的价格和库存。结算时必须重新调用商品、价格、促销和库存服务确认。

## 合并逻辑

用户登录后要合并游客购物车和用户购物车。同一 SKU 可以合并数量，数量要受限于最大购买数。
如果商品下架、库存不足或价格变化，要保留提示而不是静默删除用户意图。

合并操作要幂等，避免多端重复登录导致数量重复累加。

## 高并发和可用性

购物车读写频繁，但对一致性要求低于订单。可以使用缓存写入、异步落库、批量更新和防抖。

如果价格或库存服务不可用，购物车展示可以降级为“暂不可结算”或展示上次缓存信息，但下单前必须强校验。

## 在 eMall 项目中怎么讲？

eMall 的 `cart` 模块负责用户购买意图，和 `product`、`pricing`、`promotion`、`inventory` 在结算页聚合。
购物车可以偏高可用，订单创建则偏强正确性。

## 专家级完整回答

```text
购物车系统不是交易系统，它保存的是用户意图，而不是最终订单事实。

我会用 Redis 提供低延迟读写，用数据库做持久化和恢复。购物车记录 SKU、数量、勾选状态和加购时间，
但价格、优惠和库存只作为展示参考，结算和下单前必须重新校验。

关键点是游客购物车和登录购物车合并、多端同步、失效商品处理和高频写入优化。
购物车可以降级展示，但不能绕过下单前的强校验。
```

## 回答评分点

高分答案应该覆盖：

- 说明购物车保存购买意图，不是订单事实。
- 覆盖游客、登录、合并、多端同步和勾选。
- 能说明 Redis 加数据库的存储取舍。
- 知道价格库存要在结算和下单前重新校验。
- 能区分购物车可降级和下单强校验。
