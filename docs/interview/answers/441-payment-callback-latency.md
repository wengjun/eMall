# 441 支付回调延迟升高如何排查？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

支付回调延迟升高要先判断延迟发生在第三方通知、网关接入、签名验签、支付服务处理、订单状态更新、
Outbox 发布还是下游消费。然后按回调耗时、错误码、队列积压、数据库耗时和第三方通道拆分。

支付回调要优先保证幂等和状态正确，不能为了快而跳过校验。

## 排查范围

先确认：

- 哪个支付通道。
- 哪些商户或地区。
- 延迟从什么时候开始。
- 是否和发布重合。
- 是否有第三方公告。
- 是否只有回调慢还是支付全链路慢。

范围越清晰，定位越快。

## 链路拆分

拆分：

- 网关接收耗时。
- 验签耗时。
- 幂等查询耗时。
- 支付单更新耗时。
- 订单状态更新耗时。
- Outbox 写入耗时。
- 响应第三方耗时。

每段都要有 Trace 和指标。

## 常见原因

原因：

- 第三方重试风暴。
- 签名验签配置异常。
- 支付单表慢 SQL。
- 订单状态机锁竞争。
- 数据库连接池耗尽。
- Outbox 表膨胀。
- 回调接口被限流。

支付回调幂等不足也会放大问题。

## 在 eMall 项目中怎么讲？

eMall 支付回调变慢时，先按支付通道和错误码拆分。如果成功回调耗时主要卡在订单状态更新，就检查
订单表索引、状态机条件更新和数据库锁等待。

如果第三方重复回调增加，要确认幂等表和支付单唯一约束是否有效。
