# 534 设计内部运维补偿平台

[返回按分类学习面试题](../README.md)

## 题目

设计内部运维补偿平台。

## 先给面试官的短答案

内部运维补偿平台用于安全执行补单、补发消息、释放库存、修复状态、重试退款等生产修复动作。核心要求是权限控制、
审批、参数校验、dry run、幂等、限速、审计、回滚预案和结果可追踪。它不能变成随意改生产数据的后台。

## 适用场景

常见补偿包括支付成功但订单未更新、订单已支付但履约未创建、库存预占未释放、Outbox 事件未发送、
退款卡在处理中、搜索索引缺商品。

这些动作通常影响资金、库存或用户体验，必须受控。

## 平台能力

平台要提供补偿模板，每个模板定义参数、权限、校验规则、风险等级、执行器和审计字段。

执行前支持 dry run，展示将影响哪些订单、金额、库存或消息。高风险动作需要审批和双人确认。

执行中要支持限速、暂停、失败重试和熔断。执行后输出成功、失败、跳过和待人工处理结果。

## 安全设计

所有操作必须鉴权、授权和审计。敏感动作要使用最小权限和双人审批。

平台不应直接开放任意 SQL。修复动作要封装为明确业务 API 或受控任务，避免误操作扩大事故。

## 在 eMall 项目中怎么讲？

eMall 的 `operations` 模块可以承载补偿平台，调用 `order`、`payment`、`inventory`、`event-platform` 和 `fulfillment`
提供的受控补偿接口。`risk` 可参与高危操作审批。

## 共性系统设计模型

容量估算、数据流、失败路径、验收指标和技术取舍的统一方法见

## 专家级完整回答

```text
内部补偿平台的目标是让生产修复动作安全、可控、可审计。

我不会让运维人员直接执行任意 SQL，而是把常见修复动作封装成补偿模板。
每个模板有参数校验、dry run、权限、审批、限速、幂等和审计。

对资金、库存和履约相关动作，必须有双人审批和结果追踪。补偿平台如果没有治理，
本身就会成为生产事故来源。
```

## 回答评分点

高分答案应该覆盖：

- 覆盖补单、补发消息、释放库存、退款重试等场景。
- 强调权限、审批、dry run、幂等、限速和审计。
- 知道不能开放任意 SQL。
- 能说明补偿模板和受控业务 API。
- 能结合资金、库存、履约高风险操作说明。
