# 057 Java 服务启动慢可能有哪些原因？

[返回按分类学习面试题](../README.md)

## 核心结论

Java 服务启动慢可能来自 JVM 初始化、类加载、Spring Bean 创建、依赖扫描、数据库连接初始化、
远程配置加载、缓存预热、JIT 预热、镜像拉取、容器资源限制和启动探针配置不合理。

排查要把启动时间拆成 JVM、框架、业务初始化、外部依赖和容器平台几个阶段。

## JVM 层原因

JVM 层可能原因：

- 类加载数量很多。
- classpath 很大。
- 注解和反射使用多。
- CDS 未启用。
- JVM 参数不合理。
- 容器 CPU 太小导致初始化慢。
- 随机数源或安全初始化慢。

Java 17 本身启动能力已经比早期版本更好，但大型 Spring 应用仍然可能受类加载和反射影响。

## Spring 和框架层原因

Spring Boot 启动慢常见原因：

- 组件扫描范围过大。
- 自动配置过多。
- Bean 数量太多。
- 初始化逻辑写在 Bean 构造器或 `@PostConstruct`。
- 启动时访问远程依赖。
- 启动时执行复杂 SQL。
- 启动时加载大量配置或规则。

工程上要避免在启动路径中做重 IO、重计算和不必要的远程调用。

## 第一次请求慢

服务启动完成不代表已经充分预热。

第一次请求慢可能来自：

- JIT 尚未优化热点方法。
- 连接池还没建立连接。
- 本地缓存为空。
- 类还没被加载。
- 模板或规则首次编译。
- TLS 连接首次握手。

所以高要求服务会做启动预热和流量预热。

## 如何排查启动慢？

可以按阶段记录时间：

- main 方法开始。
- Spring context 开始。
- Bean 创建完成。
- 数据源初始化完成。
- 注册中心注册完成。
- 端口监听完成。
- readiness 通过。
- 首次预热完成。

工具上可以用：

- Spring Boot startup actuator。
- 应用启动日志时间点。
- JFR startup recording。
- 容器事件。
- Kubernetes pod events。

## 优化方式

常见优化：

- 缩小组件扫描范围。
- 减少不必要自动配置。
- 避免启动时访问非必要远程依赖。
- 重初始化异步化。
- 缓存和规则分批预热。
- 使用 readiness 控制接流量时机。
- 使用 startup probe 避免误杀慢启动应用。
- 优化镜像体积。
- 合理设置 CPU request。

核心原则是：启动路径只做必要动作，非核心动作延后或异步。
