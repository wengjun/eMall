# 341 延迟双删解决什么问题？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

延迟双删主要解决先更新数据库再删除缓存后，仍可能因为并发读、主从延迟或旧值回写导致缓存短暂
变脏的问题。

做法是在写数据库前后或写数据库后立即删一次缓存，再延迟一小段时间删第二次，清理可能被并发读
写回的旧缓存。

## 典型问题

风险流程：

- 写请求更新数据库。
- 删除缓存成功。
- 并发读请求未命中缓存。
- 并发读因为主从延迟读到旧数据。
- 并发读把旧数据写回缓存。
- 缓存里出现旧值。

第二次延迟删除用于清理这个旧值。

## 延迟时间如何选

延迟时间要参考：

- 数据库主从延迟。
- 缓存重建耗时。
- 接口平均耗时。
- 业务可接受陈旧窗口。
- 消息投递延迟。

延迟不是越长越好，过长会增加旧数据存在时间。

## 局限性

局限：

- 不能保证强一致。
- 删除操作仍可能失败。
- 需要重试和补偿。
- 延迟时间不好精确选择。
- 高并发热点场景仍要配合逻辑过期。

延迟双删是降低风险，不是分布式事务。

## 电商系统实践

商品价格更新后，大型电商系统可以先更新价格库，再删除 `pricing:sku` 缓存，随后通过延迟消息再删一次。

如果第二次删除失败，Outbox 重试继续补偿。下单时最终价格仍要由 `pricing` 服务确认，而不是完全
相信页面缓存价格。
