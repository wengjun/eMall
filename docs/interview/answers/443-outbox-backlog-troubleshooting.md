# 443 Outbox 积压如何排查？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

Outbox 积压要看事件生产速率、Relay 扫描速率、投递 MQ 成功率、数据库扫描效率、锁竞争、失败重试
和 MQ 可用性。核心指标是未发送数量、最老未发送时间和发送失败原因。

Outbox 积压会导致读模型、搜索、履约和通知延迟。

## 排查方向

方向：

- 是否业务流量突增。
- Relay 实例是否存活。
- 扫描 SQL 是否变慢。
- Outbox 表是否膨胀。
- MQ 是否不可用。
- 发送失败是否重试风暴。
- 多实例是否锁竞争。

先判断是生产太快还是消费太慢。

## 关键指标

指标：

- `NEW` 事件数量。
- `FAILED` 事件数量。
- 最老 `NEW` 事件时间。
- Relay 每秒发送数。
- MQ 发送成功率。
- 扫描耗时。
- 单批处理耗时。

最老未发送时间比总量更能体现业务影响。

## 处理方式

方式：

- 扩容 Relay。
- 优化扫描索引。
- 分片扫描。
- 限速业务写入。
- 修复 MQ 连接。
- 失败事件隔离。
- 清理历史已发送数据。

扩容前要确认不是 MQ 或数据库瓶颈。

恢复积压时要限制补发速率，优先保证实时核心事件，并监控消费者 lag。Relay 发送成功但状态更新失败会产生重复消息，
因此追赶期间必须同时验证消费幂等；永久失败的毒事件应隔离，不能阻塞整个批次。

## 电商系统实践

大型电商系统订单 Outbox 积压会导致库存、履约和搜索延迟。先看 `order-created` 事件最老未发送时间。

如果扫描 SQL 慢，应检查 `status, created_at` 索引和历史表膨胀。如果 MQ 发送失败，要优先恢复 MQ
并限速补发。
