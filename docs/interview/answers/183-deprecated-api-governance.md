# 183 如何治理废弃 API？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

废弃 API 不能直接删除，要经历声明废弃、监控使用方、通知迁移、提供替代方案、灰度下线和最终删除。
治理重点是知道谁还在用、什么时候迁、迁到哪里、下线是否安全。

对外 API 下线还涉及合同、SLA 和开发者公告，不能只按代码仓库节奏处理。

## 废弃流程

推荐流程：

- 在文档中标记 deprecated。
- 响应 Header 或元数据提示废弃。
- 提供替代接口和迁移指南。
- 监控调用方、调用量和错误率。
- 通知仍在使用的调用方。
- 设置迁移截止日期。
- 灰度拒绝或限流旧接口。
- 确认无调用后删除。

每一步都应有记录。

## 监控什么？

需要监控：

- 调用方身份。
- 调用次数。
- 调用成功率。
- 错误码分布。
- 最近一次调用时间。
- 是否来自关键客户。
- 是否有替代接口调用。

没有调用方识别，就无法安全下线。

## 兼容策略

可以使用：

- 长时间保留旧版本。
- 新旧版本双写或双读。
- 网关路由迁移。
- 返回废弃告警 Header。
- 对低风险调用方先灰度。

目标是降低调用方迁移成本，同时避免系统长期背负过多旧契约。

## 在 eMall 项目中怎么讲？

开放平台订单查询 `v1` 如果要废弃，应先发布 `v2`，给商家迁移文档，并通过网关统计每个 appKey 的调用量。

对仍调用 `v1` 的商家发送迁移通知，等调用量降到安全阈值后再灰度下线。
