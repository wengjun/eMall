# 315 如何设计数据归档系统？

[返回按分类学习面试题](../README.md)

## 核心判断

数据归档把低频历史数据从在线库迁移到历史库或对象存储，降低在线表、索引、备份和恢复压力。
它不是定时执行一条 `DELETE`，而是一条可重跑、可校验、可查询、可恢复并受合规约束的数据迁移链路。

## 数据分层和规则

- 按访问频率、业务状态和法规保留期划分热、温、冷数据，不同数据不能共用一个固定期限。
- 历史订单、支付和库存流水需要长期追溯；幂等与 Outbox 记录可按业务重试窗口设置较短保留期。
- 归档条件必须稳定，例如“完成状态且更新时间早于水位”，避免仍在变化的数据被提前迁走。
- 法律保留、诉讼冻结和隐私擦除是不同约束，删除任务必须能识别例外。

## 可恢复归档流程

1. 按时间与主键使用稳定游标切分小批次，避免 OFFSET 扫描和长事务。
2. 导出文件携带 schema 版本、主键范围、记录数和校验和，并写入归档清单状态机。
3. 在独立读取路径验证文件可读、数量一致且关键金额守恒。
4. 验证通过后先标记归档，再在低峰限速删除在线副本；任一步失败都能从批次水位重试。

删除前必须确认至少一个受保护副本和清单校验成功，删除后还要保留审计记录。

## 查询和恢复

近期数据走在线库，历史查询按时间路由到历史服务或分析平台。用户、客服、财务和审计权限应分别控制，
不能让任意历史查询回流主库。定期抽样恢复归档批次并测量 RTO；“对象存储里有文件”不等于数据可恢复。

## 电商系统中的边界

订单热数据保留期应由访问分布、法规和成本数据决定，不能直接把示例中的一到两年当生产结论。
归档任务要有 QPS、复制延迟和事务时长护栏，并在大促前暂停高风险删除阶段。
