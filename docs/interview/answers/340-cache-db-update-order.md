# 340 更新数据库和删除缓存顺序怎么选？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

常见推荐是先更新数据库，再删除缓存。因为数据库是最终数据源，写成功后删除缓存，让后续读取
重新回源加载新值。

但它仍可能出现短暂不一致，所以要结合重试、消息补偿、延迟双删、版本号和可接受陈旧窗口设计。

## 为什么不是直接更新缓存

直接更新缓存的问题：

- 并发写可能覆盖新值。
- 缓存结构可能是聚合结果。
- 更新多个缓存容易遗漏。
- 数据库提交失败会产生脏缓存。

所以更常见的是删除缓存，而不是写缓存。

## 先删缓存再更新数据库的风险

风险流程：

- 线程 A 删除缓存。
- 线程 B 读缓存未命中。
- 线程 B 读到数据库旧值。
- 线程 B 把旧值写回缓存。
- 线程 A 更新数据库成功。

结果是缓存里长期存在旧值。

## 先更新数据库再删缓存的风险

风险包括：

- 数据库更新成功，但删除缓存失败。
- 并发读在删除前读到旧缓存。
- 主从延迟导致回源读到旧值。

这些问题通过删除重试、消息补偿和短 TTL 控制。

## 电商系统实践

大型电商系统商品编辑后，应先提交数据库事务，再发送商品变更事件删除 `product:detail` 缓存。

如果删除失败，Outbox 或消息重试负责补偿。价格和库存缓存更敏感，可以用版本号或短 TTL 降低
旧值影响。下单仍以数据库或库存服务条件扣减为准。
