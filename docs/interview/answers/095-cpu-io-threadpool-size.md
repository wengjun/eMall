# 095 CPU 密集型和 IO 密集型线程池如何估算大小？

[返回按分类学习面试题](../README.md)

## 题目

CPU 密集型和 IO 密集型线程池如何估算大小？

## 先给面试官的短答案

CPU 密集型线程数通常接近 CPU 核数或核数加一；IO 密集型线程数可以更高，因为线程大量时间在等待 IO。
常见估算公式是：线程数 = CPU 核数 * CPU 目标利用率 * (1 + 等待时间 / 计算时间)。

公式只是起点，最终要通过压测和线上指标验证。

## CPU 密集型

CPU 密集型任务主要消耗 CPU。

例如：

- 加密签名。
- 压缩。
- 图片处理。
- 复杂规则计算。
- 大集合排序。

线程数太多不会让 CPU 变多，只会增加上下文切换。

通常设置为：

```text
CPU cores
CPU cores + 1
```

## IO 密集型

IO 密集型任务大量时间在等待外部系统。

例如：

- HTTP 调用。
- 数据库查询。
- Redis 调用。
- 文件读写。
- MQ 发送。

等待期间线程不占用太多 CPU，所以线程数可以高于 CPU 核数。

但不能无限高，因为线程会占用内存和下游连接。

## 估算公式

常见公式：

```text
threads = cores * targetCpuUtilization * (1 + waitTime / computeTime)
```

例如 8 核，目标 CPU 70%，任务等待 40 ms，计算 10 ms：

```text
8 * 0.7 * (1 + 40 / 10) = 28
```

可以把 28 作为初始值，再压测验证。

## 关键约束

线程池大小还受这些因素限制：

- 下游最大并发。
- 数据库连接池大小。
- HTTP 连接池大小。
- 容器 CPU limit。
- 内存和线程栈。
- P99 目标。
- 队列等待时间。

线程池大于连接池，可能只是让更多线程等待连接。

## 在 eMall 项目中怎么讲？

营销规则计算偏 CPU 密集，线程数不能远超 CPU 核数。

订单服务调用库存、价格、支付偏 IO 密集，可以设置更多线程，但必须受下游容量限制。

如果支付下游单实例只允许 100 并发，本地支付调用线程池就不能设置成 1000。

## 专家级完整回答

```text
CPU 密集型任务线程数通常接近 CPU 核数，避免上下文切换；IO 密集型线程数可以更高，
因为存在等待时间。估算可以用 cores * targetUtilization * (1 + waitTime / computeTime)。

但这只是起点，最终要看压测中的 CPU、P99、队列长度、下游连接池和错误率。线程数必须和下游容量匹配。
```

## 回答评分点

高分答案应该覆盖：

- CPU 密集型接近核数。
- IO 密集型可高于核数。
- 能说出等待时间和计算时间公式。
- 线程数受下游容量限制。
- 最终要压测验证。
