# 554 设计一次从单体到微服务的演进方案。

[返回按分类学习面试题](../README.md)

## 题目

设计一次从单体到微服务的演进方案。

## 先给面试官的短答案

单体到微服务应围绕业务边界和数据所有权渐进演进，而不是一次性重写。先建立测试、观测和模块边界，
再用绞杀者模式抽离变化快或扩容诉求强的领域，最后迁移数据并消除对单体数据库的跨域写入。

## 核心拆解

- 用领域能力、团队所有权、变更频率和容量特征选择边界，先在单体内部形成模块化依赖方向。
- 通过 API 或事件抽离能力，采用 Outbox 保证事件可靠发布；禁止新服务继续直接写单体表。
- 数据迁移经历回填、CDC、影子验证和灰度切换，契约与事件必须向后兼容。
- 每次只迁移一个可验收闭环，比较发布频率、故障隔离和成本；收益不足时停止拆分，避免分布式单体。

## 深度完善：系统设计高分展开

围绕「设计一次从单体到微服务的演进方案。」，系统设计题要按目标、规模、架构、数据、失败路径、演进六层展开。
不要只画组件图，必须讲清每个组件为什么存在，以及它如何在大促和故障场景下保持可控。

通用的六层分析、可恢复数据模型和取舍表达集中在
[共享模型：系统设计回答框架](../shared-answer-models.md#系统设计回答框架)。本题应继续围绕上文列出的领域不变量展开，
不能机械套用通用的电商表结构和中间件清单。
