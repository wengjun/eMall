# 139 阻塞式和响应式调用如何取舍？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

阻塞式调用模型简单，适合大多数 CRUD、交易和团队熟悉 MVC 的场景；响应式调用适合高并发 IO、
长连接、流式处理和端到端非阻塞链路。响应式不是天然更快，它要求数据库、缓存、HTTP 客户端和业务代码都尽量非阻塞。

如果中间大量 `.block()`，响应式收益会明显降低。

## 阻塞式模型

阻塞式模型通常是一请求一线程。

优点：

- 编程简单。
- 调试容易。
- 生态成熟。
- 团队学习成本低。

缺点：

- 大量慢 IO 会占用线程。
- 线程数过多有上下文切换和内存成本。

适合大多数同步业务。

## 响应式模型

响应式模型使用少量线程处理大量 IO 事件。

优点：

- 非阻塞 IO 资源利用率高。
- 适合长连接和流式场景。
- 背压模型更清晰。

缺点：

- 编程复杂。
- 调试栈复杂。
- 阻塞调用会破坏模型。
- 团队学习成本高。

## 选择标准

选择响应式前要确认：

- 是否端到端非阻塞。
- 数据库驱动是否支持响应式。
- 下游客户端是否非阻塞。
- 团队是否熟悉 Reactor。
- 是否有高并发长 IO 场景。
- 可观测和排障是否准备好。

否则 MVC 可能更稳。

## 交易链路考虑

订单、支付、库存这类交易链路通常更关注一致性、可读性和故障处理。

阻塞式 MVC 加合理线程池、超时、熔断和限流，往往足够稳定。

不要为了响应式增加复杂度，除非收益明确。

## 电商系统实践

大型电商系统网关、消息推送、实时库存订阅可能适合响应式。

订单创建、支付回调、库存扣减更适合同步模型和清晰事务边界。

混合架构可以存在，但每条链路内部要统一模型。
