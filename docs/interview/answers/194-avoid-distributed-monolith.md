# 194 如何避免分布式单体？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

分布式单体是代码拆成多个服务，但数据、发布、调用和变更仍高度耦合。
避免它要从业务边界、数据所有权、接口契约、独立部署、依赖治理和组织责任上同时治理。

如果一个需求必须同时改十个服务，这通常不是微服务成功，而是边界失败。

## 分布式单体的表现

表现包括：

- 多服务共享数据库。
- 服务间频繁同步调用。
- 一个需求跨多个服务联动修改。
- 接口没有稳定契约。
- 发布必须按固定顺序。
- 测试必须启动全量系统。
- 团队职责边界不清。

这些问题会让系统比单体更难维护。

## 避免方式

关键做法：

- 按业务域拆分服务。
- 明确数据所有权。
- 禁止跨服务共享写表。
- 使用稳定 API 和事件契约。
- 控制同步依赖。
- 非核心流程异步解耦。
- 每个服务可以独立测试和部署。
- 服务团队对运行质量负责。

架构边界和组织边界要匹配。

## 何时回退？

如果两个服务总是一起改、一起发布、共用数据模型，说明边界可能不合理。

可以考虑：

- 合并服务。
- 重划边界。
- 抽取公共领域能力。
- 建立读模型而不是同步穿透。

合并错误拆分不是倒退，而是治理。

## 电商系统实践

订单和库存可以独立，但不能让订单服务直接写库存表，也不能让库存服务直接改订单状态。

它们通过 API 和事件协作，各自维护自己的状态机和数据所有权。
