# 357 Redis 是否适合作为订单状态最终数据源？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

Redis 不适合作为订单状态最终数据源。订单状态涉及资金、履约、售后和审计，必须有强持久化、
事务、约束、审计和可恢复能力，通常应以关系型数据库或专门的交易存储为准。

Redis 可以做缓存、幂等短期状态、限流和临时加速，但不能替代订单库。

## 为什么不适合

原因：

- Redis 持久化可能丢失短时间数据。
- 主从切换可能丢写。
- 缺少复杂事务约束。
- 审计和追溯能力弱。
- 内存成本高。
- 淘汰策略可能影响数据。
- 运维误操作影响大。

订单状态必须可追溯、可对账、可恢复。

## Redis 可以做什么

可以做：

- 订单详情缓存。
- 下单幂等短期标记。
- 防重复提交锁。
- 秒杀令牌。
- 查询加速。
- 临时状态提示。

这些都不应该成为最终事实来源。

## 正确设计

正确设计：

- 订单库保存最终状态。
- 状态流转使用状态机。
- 唯一约束保证幂等。
- Outbox 发布订单事件。
- Redis 缓存订单查询结果。
- 缓存失效由订单变更事件驱动。

最终一致性要能通过订单库和事件追溯。

## 电商系统实践

大型电商系统订单状态以 `order` 模块数据库为准。Redis 可以缓存订单摘要，但支付成功、取消订单、发货和
退款都必须落订单库。

如果 Redis 显示状态和订单库不一致，系统应以订单库为准，并通过缓存删除或重建修复。
