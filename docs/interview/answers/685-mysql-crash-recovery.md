# 685 MySQL 崩溃恢复如何保证已提交事务不丢？

[返回按分类学习面试题](../README.md)

## 先区分三种故障

- 进程或操作系统崩溃：存储仍完好，InnoDB 自动执行 crash recovery。
- 数据页局部撕裂或损坏：可能由 doublewrite 和校验检测、修复。
- 磁盘、机房或误删除：必须依赖副本与备份，redo 不能修复已经消失的介质。

“有 redo 就永不丢数据”只对满足持久化配置且底层存储兑现 flush 语义的第一类故障成立。

## 恢复过程

1. 找到 checkpoint，识别需要恢复的表空间和日志范围。
2. 扫描 redo，把已记录但尚未反映到数据页的修改前滚到 Buffer Pool/数据页。
3. 对崩溃时处于 prepared 的内部事务，用 binlog 是否存在完整提交记录决定提交或回滚。
4. 使用 undo 回滚崩溃时仍未提交的活动事务；部分回滚可在服务恢复后继续进行。
5. 后台 purge 和刷页逐步清理历史状态。

前滚后再回滚并不矛盾：redo 保证物理结构能恢复到可继续处理的状态，undo 再消除未提交事务的逻辑影响。

## Doublewrite 解决什么

数据库页通常大于存储原子写粒度，掉电可能只写入半页。InnoDB 在覆盖最终数据文件前先把页写到 doublewrite 区；
恢复发现数据页校验失败时，可用其中完整副本恢复，再应用 redo。redo record 不能总是在结构已撕裂的页上安全重放。

## 如何验证耐久性

不能只执行优雅 `shutdown`。测试应：

- 在高并发提交时强杀进程或虚拟机，不给清理机会。
- 为每个收到成功响应的事务记录不可变业务 ID。
- 重启后验证这些 ID 全部存在，未收到明确结果的事务按幂等键核对。
- 对副本切换测试 RPO，对备份恢复执行全量校验并重放 binlog 到指定时间。

## RPO 仍取决于复制和备份

本机 crash recovery 不能覆盖整盘损坏。异步 Replica 可能落后，半同步通常只证明至少一个 Replica 收到并记录事件，
不代表已经应用；备份还可能落后更久。因此要分别声明：单机故障 RPO、可用区故障 RPO、
区域灾难 RPO 和人为误删恢复点。

在 eMall 中，我会把订单成功响应 ID 与 outbox ID 一起纳入崩溃演练，恢复后检查业务行、binlog/CDC 和事件发布状态，而不是只看 MySQL 能否启动。
