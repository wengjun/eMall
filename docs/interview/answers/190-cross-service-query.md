# 190 拆库后跨服务查询怎么做？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

拆库后不能再用数据库 Join 跨服务查询。常见方案是 API 聚合、CQRS 读模型、事件驱动冗余、搜索索引和数仓报表。
选择哪种方案取决于一致性要求、查询频率、延迟要求和数据量。

核心原则是：写模型归各服务所有，读模型可以按查询场景构建。

## API 聚合

适合：

- 数据量小。
- 实时性要求较高。
- 查询频率可控。

例如订单详情页调用订单、支付、物流和售后服务，再由 BFF 聚合返回。

问题是调用链会变长，所以要设置超时预算、并发调用、降级和缓存。

## CQRS 读模型

适合：

- 查询频率高。
- 页面需要多服务数据。
- 能接受最终一致。

做法是消费各服务事件，构建面向查询的本地读表。

例如订单列表读模型可以包含订单状态、支付状态、物流摘要和售后状态。

## 搜索和数仓

搜索适合：

- 商品搜索。
- 多条件筛选。
- 排序和分页。

数仓适合：

- 运营分析。
- 报表统计。
- 离线大查询。

不要把运营分析查询压到交易库。

## 电商系统实践

用户订单详情可以由 BFF 聚合订单、支付和物流服务。

用户订单列表可以使用订单读模型，异步接收支付和物流事件更新摘要字段。

商家经营报表应进入数据仓库，而不是跨多个交易库实时 Join。
