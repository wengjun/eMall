# 065 为什么频繁创建短生命周期对象不一定总是坏事？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

短生命周期对象通常分配在年轻代，分配快，回收也快。JVM 的分代 GC、TLAB 和逃逸分析都让小对象创建成本较低。
如果为了避免对象而牺牲代码可读性，可能得不偿失。

但“不一定坏”不代表“永远没问题”。高分配速率、大对象和对象晋升仍然会造成 GC 压力。

## 为什么短生命周期对象友好？

现代 JVM 的假设是：大多数对象很快死亡。

这非常符合 Web 服务场景：

- 请求 DTO。
- 响应 DTO。
- 参数对象。
- 临时计算结果。
- 局部集合。

这些对象在请求结束后很快不可达，年轻代 GC 可以高效回收。

## 分配快

短生命周期小对象通常在 Eden 区分配。

由于 Eden 内存相对连续，分配可以通过指针碰撞完成。

加上 TLAB，多线程分配也不需要频繁争抢全局锁。

所以创建普通小对象的成本通常低于很多人想象。

## 回收快

年轻代 GC 不会逐个释放死亡对象。

它只需要找到存活对象并复制到 Survivor 或老年代。

如果大部分对象已经死亡，回收成本反而较低。

这就是短生命周期对象适合年轻代的原因。

## 可读性也很重要

业务代码中，小对象经常用于表达概念。

例如：

```java
record Money(long cents) {
}

record SkuQuantity(long skuId, int quantity) {
}
```

这些对象让代码更清晰，减少参数顺序错误。

如果为了少创建对象，把所有字段拆成散乱的 primitive 参数，可能更容易出错。

## 什么时候会变坏？

短生命周期对象过多也可能有问题。

风险包括：

- allocation rate 极高。
- young GC 过于频繁。
- 对象不是小对象。
- 对象存活跨过多次 GC 后晋升老年代。
- 临时集合容量过大。
- 日志和 JSON 产生大量字符串。
- 缓存或队列让对象生命周期变长。

所以关键不是“创建对象次数”，而是“分配速率、对象大小和存活时间”。

## 不要盲目复用对象

对象复用看似减少分配，但会带来：

- 状态残留。
- 线程安全问题。
- 生命周期变复杂。
- 更难测试。
- 更容易进入老年代。

在 Java 服务中，对象复用通常只适合资源型对象，例如连接、线程、缓冲区。

普通业务对象更应该保持简单、不可变、短生命周期。

## 在 eMall 项目中怎么讲？

订单计算中创建 `Money`、`OrderLine`、`DiscountResult` 这类短生命周期值对象是可以接受的。

它们能提升业务表达力，并且 JVM 对小对象很友好。

但如果营销规则一次计算创建几十万个中间对象，或者 JSON 序列化产生大量大字符串，就要通过 JFR 找热点并优化。
