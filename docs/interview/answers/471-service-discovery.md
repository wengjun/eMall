# 471 服务发现如何工作？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

服务发现解决的是“调用方如何找到目标服务实例”的问题。它通常由服务注册、健康检查、服务查询、负载均衡、
实例摘除和缓存刷新组成。在 Kubernetes 中，Pod 变化会被 EndpointSlice 记录，Service 提供稳定虚拟地址，
CoreDNS 提供名称解析，调用方通过服务名访问后端实例。

## 基本过程

典型服务发现链路如下：

1. 服务实例启动后注册自己的地址、端口、版本、机房、权重和健康状态。
2. 注册中心或平台持续做健康检查，剔除不可用实例。
3. 调用方根据服务名查询可用实例列表。
4. 客户端或网关按负载均衡策略选择实例。
5. 实例扩缩容、重启、发布时，调用方通过 watch、DNS TTL 或缓存刷新感知变化。

在 Kubernetes 中，服务发现不需要业务实例主动写注册中心。控制面根据 Pod label 选择后端 Pod，并把结果写入
EndpointSlice。Service 名称会被 CoreDNS 解析，调用方访问 `order.default.svc.cluster.local` 即可找到订单服务。

## 客户端发现和服务端发现

客户端发现指调用方拿到实例列表后自己选择目标实例，例如通过注册中心 SDK、Ribbon 或自研客户端实现。
优点是灵活，能做区域优先、权重、灰度和本地容错；缺点是每种语言都要维护客户端逻辑。

服务端发现指调用方只访问一个稳定入口，由负载均衡器、网关、Service 或 Service Mesh 选择后端实例。
优点是业务简单、语言无关；缺点是入口组件成为关键基础设施，需要高可用和清晰的流量策略。

## 生产系统的关键点

服务发现不能只看“能不能找到服务”，还要看变化时是否稳定。生产系统要控制 DNS TTL、客户端缓存时长、
连接池淘汰、灰度标签、实例权重、跨可用区路由、异常实例摘除和恢复探测。

调用方不能无限相信注册中心。即使服务发现返回了实例，也要结合超时、重试、熔断、限流和连接池失败摘除。
否则一个刚恢复但仍然慢的实例会被大量流量打满，引发二次故障。

## 在 eMall 项目中怎么讲？

eMall 的订单、库存、支付、促销、风控等服务可以通过 Kubernetes Service 做基础发现。对关键交易链路，
还可以在网关或服务治理层叠加灰度标签、区域优先和异常实例摘除。

面试时可以强调：服务发现只是入口，真正的稳定性来自发现、路由、健康检查、熔断和自动恢复的组合。
