# 704 SBOM、制品签名和构建来源证明如何保护供应链？

[返回按分类学习面试题](../README.md)

## 三个机制回答三个问题

- SBOM：这个制品声明包含哪些组件、版本和许可证？
- 制品签名：当前拉取的字节是否是被授权主体签过且未被篡改的对象？
- Provenance：它由哪个构建器、基于什么源码和参数、通过什么过程生成？

只有 SBOM 不能证明 jar 没被替换；只有签名不能证明签名者使用了可信源码；只有 provenance 没有验证策略也只是元数据。

## 一条可验证流水线

```text
受保护源码提交
 -> 隔离、短生命周期构建器
 -> Maven 依赖解析与测试
 -> 镜像按 digest 产出
 -> 生成 SBOM + provenance
 -> 使用工作负载身份签名
 -> Registry 保存不可变对象
 -> 部署准入验证签名、来源和策略
```

部署必须引用镜像 digest，而不是可被覆盖的 `latest` 标签。签名对象、SBOM 和 provenance 都应绑定同一个 digest。

## Java/Maven 依赖治理

- 父 POM 或 BOM 统一锁定版本，禁止不可审计的动态版本。
- CI 输出完整依赖树，识别传递依赖、scope 和 shaded jar。
- 依赖漏洞扫描与许可证策略不能只看 direct dependency。
- 私服代理上游仓库，限制发布权限并保留校验和与审计。
- 构建环境禁止从开发者本机缓存偷偷带入未声明产物。

漏洞扫描结果必须结合可达性和业务暴露面排序，但严重漏洞的临时豁免要有 owner、到期时间和补偿控制。

## SLSA 思路

SLSA Build Track 逐步提高 provenance 完整性和构建抗篡改能力。关键不是追求一个徽章，而是让“开发者不能在正常流程外悄悄替换生产制品、构建服务也留下可验证证据”成为可执行策略。

密钥应由 KMS 或短期工作负载身份管理，避免把长期私钥放 CI 环境变量。验证端信任的是受控身份、仓库、分支和构建器组合，不是“有任意签名即可”。

## eMall 事件响应

发现某 Log/JSON 组件漏洞时，先用 SBOM 精确定位受影响镜像和环境；重建后验证新 digest、签名与 provenance；
准入策略阻止旧 digest 再部署。若构建身份疑似泄露，则撤销信任并重签可信重建物，而非只升级依赖版本。
