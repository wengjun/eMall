# 585 你为什么选择微服务而不是单体？

[返回按分类学习面试题](../README.md)

## 核心判断

不是因为微服务天然更先进，而是本项目包含订单、库存、支付、履约等不同业务域，它们的变更节奏、容量模型和故障等级不同，需要独立发布、扩缩容和隔离。代价是远程调用、最终一致性、运维平台和组织协作都明显更复杂。

## 取舍依据

- 领域边界是否稳定，数据是否能够归属到单一服务，而不是按 Controller、Service、DAO 技术分层拆分。
- 某个领域是否需要独立扩容、独立发布或独立故障隔离；没有这些需求时，拆分收益很低。
- 团队是否具备契约测试、可观测性、自动化发布、容量治理和事件一致性能力。
- 服务间调用链是否可控；拆完仍共享数据库、同步互调，得到的只是分布式单体。

## 项目证据与边界

eMall 以领域数据所有权、API 契约、Outbox、幂等和独立部署表达微服务边界。若团队较小或业务仍在快速试错，模块化单体更合适；应先保持清晰模块边界，再按真实瓶颈拆分，而不是一次性拆成大量进程。
