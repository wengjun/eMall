# 599 你如何避免 common 变成强耦合中心？

[返回按分类学习面试题](../README.md)

## 核心判断

通过依赖方向、发布边界和准入规则治理 common，而不是只靠代码评审提醒。common 必须是叶子依赖：它不能反向依赖任何业务模块，也不能暴露业务服务的内部模型。

## 取舍依据

- 按 `api`、基础实现和 starter 拆分，使用方只引入所需能力。
- 禁止通用 DTO 演变成全站领域模型；跨服务契约独立版本化。
- 用 Maven Enforcer 或架构测试阻止循环依赖、禁止依赖和越层访问。
- 破坏性修改走弃用期、兼容测试和迁移说明，避免全仓同步升级。

## 项目证据与边界

每次抽取都应回答“谁拥有语义、谁负责兼容、失败会影响谁”。若答案仍属于订单或支付域，就留在对应模块，即使复制少量适配代码也比形成中心耦合更安全。
