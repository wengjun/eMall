# 182 如何设计跨服务错误码映射？

[返回按分类学习面试题](../README.md)

## 先给面试官的短答案

跨服务错误码不能简单把下游原始错误透传给上游或客户端。每个服务应把下游错误映射为本服务语义下的稳定错误码，
同时保留 `traceId` 和内部诊断信息。

错误码映射要区分业务失败、系统失败、可重试失败和降级结果。

## 为什么不能直接透传？

直接透传有问题：

- 暴露下游内部实现。
- 上游被迫理解所有下游错误。
- 下游错误码变化会破坏上游兼容。
- 用户看到的信息不符合当前业务语义。
- 错误码数量失控。

服务边界不仅包括数据和接口，也包括错误语义。

## 映射原则

原则包括：

- 对外错误码表达当前服务语义。
- 下游错误码只作为内部原因。
- 保留 `traceId` 关联完整链路。
- 区分永久失败和临时失败。
- 区分用户可纠正和系统不可控。
- 统一记录原始错误和映射结果。

比如库存服务返回 `SKU_STOCK_NOT_ENOUGH`，订单服务可以映射为 `ORDER_ITEM_OUT_OF_STOCK`。

## 错误分类

常见分类：

- 参数错误。
- 权限错误。
- 资源不存在。
- 业务规则冲突。
- 下游超时。
- 下游不可用。
- 限流。
- 系统内部错误。

调用方应根据分类决定是否重试、提示用户或进入补偿。

## 在 eMall 项目中怎么讲？

订单服务调用支付服务失败时，不能把支付内部的数据库错误直接返回给用户。

订单服务应返回 `ORDER_PAYMENT_TEMPORARILY_UNAVAILABLE`，标记 `retryable=true`，内部日志记录支付服务原始错误码、
HTTP 状态、耗时和 traceId。
